# Gana quality baseline

This is the original exploratory measurement. The repeatable, hash-locked
workflow is documented in [REPRODUCIBLE_BASELINE.md](REPRODUCIBLE_BASELINE.md),
with its reviewed reference under `quality/baselines/2026-09-21/`. Use the
**Gana: Reproducible Baseline** task for future full measurements.

Measured on 2026-09-21 against version 1.0.14, branch `main`, commit
`8b61ba5d62bc0be3d48722896e08cf89945908a4`, including the existing local
one-line change in `src/gana/sets/parameter.py`. The untracked, empty
`docs/examples/insurance.ipynb` was not executed. Neither file was changed.

## Running the VS Code tasks

Open a Gana file, run **Python: Select Interpreter**, and select an environment
containing Gana's dependencies, Radon, pytest, pytest-cov, and Hypothesis.
The existing shared environment used for this baseline is:

```text
/Users/cacodcar/Research/kuru/.venv/bin/python
```

Run **Tasks: Run Task** and select **Gana: All Quality Checks**, or select an
individual Gana task. **Tasks: Run Test Task** selects the coverage task.

The tasks use the Python extension's selected interpreter and the Gana folder
as their working directory. They inspect `src/gana` and run `tests`; they do
not install dependencies, format code, or apply fixes. The coverage task also
measures branches. The complexity filter is labeled **B or worse** because
`--min B` displays grades B through F, not grades better than B.

Running the test task can create `.coverage`, pytest/Hypothesis caches, and
MPS/solution files in Gana because the current tests and solver code write
relative paths. The initial baseline below was instead run from a fresh
temporary working directory so existing workspace files were not overwritten.
Do not run solver tests in a directory containing valuable same-named exports.

These tasks are manual checks, not automatic edits or CI gates. Radon reports
grades but does not make a high complexity score fail the task. No arbitrary
coverage threshold has been imposed.

## How approved changes should use this baseline

Compare complexity and maintainability for affected functions/modules, and
explain changes in raw size. Add semantic regression tests for changed behavior
and report statement and branch coverage separately. Do not trade correctness
for a better average score, remove meaningful coverage targets, or rewrite
unrelated code solely to improve metrics.

The first priorities remain regression coverage for expression coefficients,
zero/constant handling, indexing, export semantics, and solver-result integrity.
Refactor the high-complexity expression paths incrementally after these tests
exist. Display/LaTeX hotspots can follow mathematical correctness work.

Source code and existing tests were not modified to obtain this baseline.
Future implementation still requires the user's explicit approval.
